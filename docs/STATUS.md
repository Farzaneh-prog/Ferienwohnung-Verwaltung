# وضعیت پروژه — سند انتقال (۲۰۲۶-۰۹-۱۶)

این فایل برای شروع یک مکالمه جدید نوشته شده — خلاصه‌ی دقیق «الان کجاییم»، بدون نیاز
به مرور تاریخچه طولانی مکالمه قبلی. اسناد اصلی (`سند-معماری-سیستم-مهمانخانه.md` و
`نظافتچی_ها-و-فرمول_های-مالی.md`) هنوز روی دیسک هستن و باید دوباره خونده بشن — این
فایل جایگزینشون نیست، فقط می‌گه واقعیت پیاده‌سازی‌شده کجاها با اون اسناد فرق کرده.

## ۳. مسیر داده — چطور یک رزرو وارد فایل می‌شود

۱. شما از Booking.com Extranet یا Airbnb Host، export رسمی می‌گیرید (نه Cowork، نه اسکرپینگ)
۲. `/import` → آپلود → `import_parser.py` تشخیص می‌ده فرمت کدومه و پارس می‌کنه
۳. اگه یه کد رزرو توی چند فایل باشه، `merge_reservation_entries` فیلد به فیلد **ترکیب** می‌کنه (نه فقط یکی رو انتخاب) — چون AA و AX به داده‌ی هم‌زمان از هر دو فایل بوکینگ نیاز دارن
۴. پیش‌نمایش (جدید/تکراری/کنسلی) → تأیید → `xlsx_writer.process_batch`
۵. `append_reservation`: ردیف جدید **فقط به یه ردیف خالی/انتهای شیت درست اضافه می‌شه**، هیچ‌وقت وسط شیت درج نمی‌شه (چون openpyxl هنگام درج/حذف ردیف، فرمول ردیف‌های دیگه رو خودکار اصلاح نمی‌کنه — بر خلاف خود اکسل)
۶. فرمول‌ها یا از یه ردیف مجاور «کپی» می‌شن (`clone_formulas`) یا برای ستون‌های حساس، **صریح نوشته می‌شن** (`EXPLICIT_FORMULAS`/`EXPLICIT_LITERALS`) — بخش ۵ رو ببینید
۷. کنسلی → هیچ‌وقت حذف نمی‌شه، فقط ستون `Storniert` (BB) = `ja` می‌شه (چون حذف فیزیکی هم همون مشکل فرمول رو داره)

## ۴. چیزی که هیچ export ای نمی‌ده — همیشه دستی

- **اسم مهمان و ایمیل**: هیچ‌کدوم از سه فرمت export (نه Booking ساده، نه مفصل، نه Airbnb) این رو نمی‌ده. همیشه placeholder (`Gast (Code XXXX)`) می‌مونه تا از `/complete` پر بشه
- **تعداد بزرگسال/کودک**: فقط توی Booking «مفصل» هست؛ Booking «ساده» و Airbnb ندارن
- **`/complete` فعلاً فقط ۴ فیلد داره**: اسم، ایمیل، بزرگسال، کودک — چیزهای دیگه‌ای که ممکنه لازم بشه (مثلاً اگه یه فیلد مالی از یه پلتفرم خاص نیومد) هنوز اضافه نشده؛ باید لیست دقیق «کدوم فیلد از کدوم پلتفرم میاد/نمیاد» کامل بشه و فرم بر همون اساس تکمیل بشه

## ۵. وضعیت دقیق هر ستون فرمولی (مهم‌ترین بخش برای بازبینی)

### ✅ صریحاً توسط شما تأیید و کد شده (`xlsx_writer.py`)
| ستون | فرمول/مقدار | منبع |
|---|---|---|
| I, J | `=F*G`, `=H*F` | ساختاری |
| M (Übernachtungssteuer) | `=G*F` | تأیید مستقیم |
| O (Gezahlt) | `=Preis+M` (Preis از export) | تأیید مستقیم |
| P (Putzarbeit) | Booking: نرخ ثابت ۵۰(Karlstraße)/۶۵(Eisenach) — Airbnb: `Reinigungsgebühr` واقعی | تأیید مستقیم |
| Z (Umsatzsteuersatz) | همیشه `0.19` | تأیید مستقیم |
| AA (Nettobetrag) | `Commission amount`(Booking) یا `Servicegebühr`(Airbnb) — هر دو پلتفرم؛ کامنت قدیمی کد که می‌گفت «فقط Booking» اشتباه بود، خودِ کد از اول برای هر دو کار می‌کرد، فقط کامنت ۲۰۲۶-۰۹-۱۶ اصلاح شد | تأیید مستقیم |
| AF (Endreinigung) | `=IF(R="ja",P,P/1.07)` — همه پلتفرم‌ها | تأیید مستقیم |
| AG (Stellplatz) | همیشه `0` | تأیید مستقیم |
| AK | `=IF(AQ="ja",AJ,AJ/1.07)` | تأیید مستقیم |
| AL | `=AK*1.07` | تأیید مستقیم |
| AM | `=AJ` | تأیید مستقیم |
| AV (متن پیام پرداخت) | فرمول کامل ۴حالته (Airbnb/booking/پرداخت‌شده/Vrbo) | تأیید مستقیم |
| AX (Payment Charge von Booking) | `Commission(ساده) − AA` — **فقط Booking** | تأیید مستقیم |
| BC (چک‌سام) | `=AF+AH+AN+AO+AP-AE+AG` | تأیید مستقیم |
| S | placeholder `0` | تأیید مستقیم (موقت، بعداً واقعی) |
| T | placeholder `3.5` | تأیید مستقیم (موقت) |
| U | `=T*12` | تأیید مستقیم |
| V | placeholder `"M-Ü"` | تأیید مستقیم (موقت) |
| AN (Zimmergesamt) | `=ROUND(AK*F,2)` | مستند در سند `نظافتچی_ها...` (۲۰۲۶-۰۹-۱۶ هاردکد شد) |
| AO (7% Steuer) | `=IF(AQ="ja","§13b UStG",ROUND((AN+AF)*0.07,2))` | مستند در سند (۲۰۲۶-۰۹-۱۶ هاردکد شد) |
| AP (19% Steuer) | `=IF(AQ="ja","§13b UStG",ROUND(AG*0.19,2))` | مستند در سند (۲۰۲۶-۰۹-۱۶ هاردکد شد) |
| AR (Netto) | `=AN+AF+AG+AH` | مستند در سند (۲۰۲۶-۰۹-۱۶ هاردکد شد) |
| AS (Zimmer) | `=ROUND(AK,2)` | مستند در سند (۲۰۲۶-۰۹-۱۶ هاردکد شد) |
| AT (متن Stellplatz) | Karlstraße: `IF(B="Airbnb",", exkl. Stellplatz.",IF(B="booking",", exkl. Stellplatz.","."))` / Eisenach: همون با «inkl.» (بر اساس property نه sheet؛ ۲۰۲۶-۰۹-۱۶ فرمول nested-IF دقیق جایگزین نسخه‌ی OR() شد که رفتارش یکی بود ولی متنش فرق داشت) | مستند در سند + تأیید مستقیم |
| AU (Komm-label) | `=IF(B="Airbnb","Airbnb Bestätigungscode: ",IF(B="booking","Booking number: "," "))` | مستند در سند (۲۰۲۶-۰۹-۱۶ هاردکد شد) |
| BE (Verdient pro nacht) | `=Q/F` | مستند در سند (۲۰۲۶-۰۹-۱۶ هاردکد شد) |
| Q (Verdient) | `=IF(B="booking",O-U-M-AA-AX-AO,O-U-M-AA-AX-AO-AP)` | تأیید مستقیم ۲۰۲۶-۰۹-۱۶ |
| AB | `=AA*0.19` | تأیید مستقیم ۲۰۲۶-۰۹-۱۶ |
| AC | `=AA+AB` | تأیید مستقیم ۲۰۲۶-۰۹-۱۶ |
| AE | `=O` | تأیید مستقیم ۲۰۲۶-۰۹-۱۶ |
| AH | `=M` | تأیید مستقیم ۲۰۲۶-۰۹-۱۶ |
| AI | `=IF(AQ="ja",AE-AF-AG-AH,AE-AF*1.07-AG*1.19-AH)` | تأیید مستقیم ۲۰۲۶-۰۹-۱۶ |
| AJ | `=AI/F` | تأیید مستقیم ۲۰۲۶-۰۹-۱۶ |

**نتیجه:** بخش «⚠️ کپی از ردیف مجاور، تأییدنشده» قبلی (Q، AB، AC، AE، AH، AI، AJ
+ AN، AO، AP، AR، AS، AT، AU، BE) کاملاً بسته شد — همه‌ی این ۱۵ ستون الان یا از
سند طراحی یا مستقیم توسط فرزانه (۲۰۲۶-۰۹-۱۶) تأیید و هاردکد شدن.

### ❌ همیشه خالی می‌مونه — تصمیم دستی/کسب‌وکاریه
`K (Private Zweck)، R (Ausländische Firma)، W (Fahrtkosten)، AD (Adresse)،
AQ (Ausländische Firma - همون هدر تکراری)، AW (bereits überwiesen)،
AY (Paypal)، AZ (رزرو برای فلگ مالیات، فاز بعد)`

**L (Arbeitszweck) — تصمیم نهایی ۲۰۲۶-۰۹-۱۶: دستی می‌مونه.** سن کودک واقعاً
توی export «مفصل» Booking هست (`Children's age(s)`)، ولی فرزانه ترجیح داد
خودش دستی وارد کنه؛ گفت اگه اصلاً واردش نکنه هم مهم نیست. پس نه پارسر تغییر
کرد، نه فرمی برای K/L ساخته شد — عمداً.

**X (Rechnungsnummer) — تصمیم نهایی ۲۰۲۶-۰۹-۱۶: دستی می‌مونه.** برای همه‌ی
رزروها لازمه، ولی باید دقیقاً به ترتیب تاریخ ورود شماره‌گذاری بشه — و چون
ردیف‌های جدید ممکنه توی شکاف وسط شیت درج بشن نه لزوماً انتهای فیزیکی
(بخش ۶.۴ بالا)، یه شمارنده‌ی خودکار ساده («آخرین X زوج + ۲») نمی‌تونه تضمین
کنه ترتیب تاریخی درست بمونه وقتی یه رزرو با تاریخ قدیمی‌تر بعداً اضافه بشه.
فرزانه تشخیص داد خودش دستی انجام بده راحت‌تره.

## ۶. کشف‌های فنی مهم (برای جلوگیری از تکرار اشتباه)

1. **`ws.cell(row, col, value=None)` در openpyxl هیچ کاری نمی‌کنه** (چون `None`
   سنتینل «مقداری داده نشده»ست) — همیشه `cell.value = None` مستقیم.
2. ستون‌های `R` و `AQ` **دقیقاً همون متن هدر** رو دارن (`Ausländische Firma mit
   steuer in Heimat`) — نگاشت بر اساس اسم هدر نمی‌تونه بینشون فرق بذاره؛ برای همین
   فرمول‌های `EXPLICIT_FORMULAS` مستقیم با حرف ستون (نه اسم فیلد) آدرس‌دهی می‌شن.
3. برخی ردیف‌های قدیمی، فرمول رو به‌صورت **متن/عدد چسبونده‌شده** دارن نه فرمول زنده
   (مثلاً `AV` گاهی متن ثابت بود، `BC` نسخه‌ی قدیمی/ناقص فرمول رو داشت) — یعنی
   «کپی از ردیف مجاور» به‌تنهایی قابل‌اعتماد نیست.
4. ردیف‌های خالی وسط شیت (از پاک‌کردن دستی قبلی با Delete، نه حذف کامل ردیف) به‌عنوان
   «جای خالی قابل‌استفاده» در نظر گرفته می‌شن — ردیف جدید می‌تونه توی یه شکاف وسط
   شیت بیفته، نه لزوماً انتهای فیزیکی؛ این عمدیه (امن‌تر از همیشه انتهای شیت).

## ۷الف. کنسلی‌ها + پاک‌کردن دستی — `known_codes.json` (۲۰۲۶-۰۹-۲۳)

فرزانه ردیف‌های کنسل‌شده رو کامل از GästeListe پاک می‌کنه (نه فقط
Storniert=ja)، چون جمع‌کل‌های سالانه (Übersicht/ÜbersichtSteuer) فرمول
`SUM()` ساده‌ن — حدود ۲۷۱ فرمول توی هر دو فایل، هیچ‌کدوم Storniert رو
حساب نمی‌کنن — و پاک‌کردن تنها راهی بود که جمع‌ها درست بمونن. مشکلش این
بود که پاک‌کردن یعنی هیچ ردی از کد رزرو نمی‌مونه، پس یه export قدیمی‌تر که
دوباره آپلود بشه، اون رزرو رو «جدید» می‌بینه و دوباره اضافه می‌کنه (این
دقیقاً همون چیزی بود که با `HMEX45DNAJ` دیدیم).

**راه‌حل انتخاب‌شده (نه SUMIFS):** `app/known_codes.py` — یه فایل JSON
جدا (`data/known_codes.json`، از قبل gitignore شده) که هر کدی که این اپ
تا حالا اضافه یا کنسل کرده رو برای همیشه نگه می‌داره، مستقل از خودِ
GästeListe. `get_existing_confirmation_codes` (چک تکراری‌بودن ایمپورت)
الان این لیست رو هم چک می‌کنه. تست شد: اضافه → دستی پاک از اکسل → دوباره
آپلود همون کد → درست به‌عنوان تکراری رد شد.

**چرا نه SUMIFS:** تبدیل ۲۷۱ فرمول به `SUMIFS(..., BB:BB, "<>ja")` هم
جواب می‌داد، ولی روی ارقام مالیاتی اثر می‌ذاره و نیاز به بازکردن فایل
واقعی توی اکسل برای تأیید اعداد داشت — فرزانه این راه سبک‌تر و بدون‌ریسک
رو ترجیح داد.

**یافته‌ی جانبی که هنوز حل نشده:** شیت `Muster` اصلاً ستون `Storniert`
رو توی هدرش نداره (برخلاف شیت‌های فصلی که BB='Storniert' دارن) — یعنی
اگه یه رزروِ پارک‌شده توی Muster (سال بعد) کنسل بشه، `apply_cancellation`
نمی‌تونه پرچمش کنه (بی‌صدا رد می‌شه). با راه‌حل `known_codes.json` این
دیگه مشکل دِدوپ ایجاد نمی‌کنه، ولی خودِ ستون Storniert توی Muster هنوز
خالیه — اگه لازم شد جدا درستش کنیم.

## ۷. Putzplan (برنامه نظافتچی) — خودکارسازی جدید (۲۰۲۶-۰۹-۲۲)

`Putzplan2026.xlsx` — یه فایل کاملاً جدا از GästeListe، یه شیت تخت
(`Tabelle1`) بدون هیچ فرمولی، ۱۰ ستون (A تا J؛ جزئیات کامل هر ستون توی
`app/putzplan_writer.py`). از این به بعد، هر رزرو جدیدی که از `/import`
تأیید بشه یه ردیف خودکار اینجا هم می‌گیره — `app/putzplan_writer.py`،
وصل‌شده به `xlsx_writer.process_batch`.

**نکته‌ی مهم — ستون C اول اشتباه فهمیده شده بود:** اولین نسخه‌ی این ماژول
فرض کرد ستون C (Datum) تاریخ *ورود* مهمانه (بر اساس تطبیق آماری با
GästeListe که گمراه‌کننده بود، چون فایل به‌مرور دستی دریفت کرده). فرزانه
همون روز تصحیح کرد: **ستون C تاریخ *خروج* مهمانه** (Abreise) — چون نظافت
معمولاً به محض خروج مهمان انجام می‌شه. قبل از اینکه نسخه‌ی اشتباه به داده‌ی
واقعی برسه اصلاح شد.

**نگاشت نهایی:**
- **C (Datum)** = Abreise Datum (خروج) رزرو
- **D (Tag)** = روز هفته‌ی همون تاریخ خروج
- **F (Buchung für gleichen Tag)** = «Ja» اگه رزرو *بعدی* (نزدیک‌ترین
  Anreise غیرکنسلی بعد از این خروج، توی همون ملک) دقیقاً همون روز باشه
- **G, H (Erwachsene, Kinder unter 18)** — **تصحیح ۲۰۲۶-۰۹-۲۴:** تعداد
  بزرگسال/کودک **رزرو بعدی** (کسی که داره میاد)، نه رزروی که داره خارج

## ۱۰. برای شروع مکالمه بعدی

پیشنهاد می‌شه اول این فایل خونده بشه، بعد دو سند اصلی (`سند-معماری...`,
`نظافتچی_ها...`) دوباره کنار هم با این فایل مقایسه بشن تا مشخص بشه دقیقاً کجاها
باید رسماً به‌روزرسانی بشن یا فاز‌بندی از نو تعریف بشه.

**وضعیت فعلی (۲۰۲۶-۰۹-۲۴):** خوندن و نوشتن داده (import، تکمیل اطلاعات،
کنسلی، Putzplan خودکار، فرمول‌های مالی) کامل و تست‌شده‌ست — بخش‌های ۵، ۷،
۷الف بالا رو ببین. فرزانه تأیید کرد این بخش «جواب می‌ده» و می‌خواد بریم
سراغ فاز بعدی، توی یه پنجره‌ی مکالمه‌ی جدید.

**۴ فاز بعدی که فرزانه مشخص کرد (۲۰۲۶-۰۹-۲۴):**

1. **Frontend مناسب** — رابط فعلی (`login`, `/import`, `/complete`,
   `/alerts`, `/reservations`) خیلی خامه، فقط برای تست کار می‌کرد. باید
   با فرزانه دقیق صحبت بشه که کجاش براش سخته/گیج‌کننده‌ست، و آیا بازطراحی
   همین Flask+Jinja کافیه یا نیاز به یه چیز جدی‌تره.
2. **یادآوری یک روز قبل از ورود مهمان** — به خودِ فرزانه. کانال هنوز
   مشخص نیست (لیست داخل اپ / تقویم / واتساپ — بخش ۹.۷ قبلاً این بحث رو
   باز کرده بود). اگه واتساپ انتخاب بشه، دقیقاً همون وابستگی میزبانی زیر
   رو داره.
3. **هماهنگی نظافتچی‌ها از طریق واتساپ** — الگوریتم کامل چرخش/اسکیلیشن
   قبلاً توی `نظافتچی_ها-و-فرمول_های-مالی.md` و سند معماری مستند شده
   (جنیفر/مهرناز → Manuela → تهمینه/Ramic، با قوانین هفته مرخصی و غیره).
   نیازمندی‌های ساخته‌نشده: (الف) **تصمیم میزبانی عمومی** — وب‌هوک ورودی
   Twilio (جواب «بله» نظافتچی) نیاز به آدرس عمومی داره، اپ فعلاً فقط
   لوکاله؛ گزینه‌ها قبلاً بررسی شده (میزبانی مستقیم Flask، یا رله از
   طریق وردپرس مارکت‌رزیدنس — بخش ۸ رو ببین). (ب) **روستر در‌دسترس‌بودن
   نظافتچی‌ها** — چیزی که فاز‌های بعدی (مثل اسکیلیشن Putzplan، بخش ۹.۸)
   هم منتظرشن.
4. **آپدیت خودکار اکسل بعد از اتمام نظافت** — وقتی نظافتچی از طریق
   واتساپ تأیید کنه کارش تمومه، اسم واقعیِ همون نظافتچی + قیمت (بر اساس
   جدول نرخ در `نظافتچی_ها...`) باید بره توی ستون‌های V (کد نظافتچی) و
   T/U (ساعت/دستمزد) — این ستون‌ها الان placeholder دارن (بخش ۵). مستقیم
   وابسته به فاز ۳ (سیگنال «کی و کِی تأیید کرد» باید از همون‌جا بیاد).

**نکته‌ی مشترک فازهای ۲ تا ۴:** هر سه به همون **تصمیم میزبانی عمومی**
که در بخش ۹.۶/۹.۷ باز مونده وابسته‌ن — بهتره این تصمیم اول گرفته بشه، نه
که سه بار جدا جدا بهش برسیم.

## ۱۴. فاز ۳ (هماهنگی واتساپ نظافتچی) — بازبینی طراحی + Stage 0 ساخته شد (۲۰۲۶-۰۹-۳۰)

قبل از شروع کدنویسی، طراحی سند معماری (بخش ۴) با وضعیت واقعی الان
مقایسه شد. نتیجه: الگوریتم اصلی (زنجیره اولویت ۴سطحی، تایم‌لاین
اسکیلیشن، قانون هفته مرخصی) هنوز درسته، ولی دو تا چیز باید عوض بشه:

1. **این فاز باید مستقیم به Putzplan خودکار (که الان وجود داره) وصل
   بشه**، نه یه سیستم جدا — یعنی وقتی نظافتچی «بله» جواب داد، مستقیم
   توی ستون A همون ردیف Putzplan نوشته می‌شه. عملاً یعنی فاز ۳ و ۴ (که
   قبلاً جدا تعریف شده بودن) خیلی به هم نزدیک‌ترن.
2. **این فاز واقعاً به Scheduler نیاز داره** — بر خلاف فاز ۲ که عمداً
   event-driven کردیمش. اینجا trigger «۱۰ روز مونده» یا «۱ ساعت گذشته،
   هنوز جواب نیومده» ذاتاً زمان‌محوره. APScheduler هنوز اضافه نشده —
   قراره Stage 1 اضافه بشه.

**تصمیم‌های گرفته‌شده (۲۰۲۶-۰۹-۳۰):**
- **Twilio** انتخاب شد، نه اتوماسیون غیررسمی واتساپ (همون ریسک ToS که
  برای Airbnb/Booking.com قبلاً باعث توقف اون مسیر شد، اینجا هم صادقه).
- **حساب Twilio رایگان (Trial + WhatsApp Sandbox) برای الان کافیه** —
  فقط وقتی رفتیم production واقعی نیاز به ارتقا داره.
- **روستر نظافتچی‌ها فعلاً یه فایل JSON دستی‌ویرایش‌شونده** (نه صفحه‌ی
  تنظیمات داشبورد — چون فاز ۱ فرانت‌اند هنوز ساخته نشده).
- **ساخت پله‌پله**، نه یکجا — نقشه راه پایین.
- شماره‌ی واتساپ production (فاز production Twilio، نه الان) روی یه
  سیم‌کارت قدیمیه که فرزانه داره؛ برای ثبت فقط یه‌بار نیاز به دریافت
  پیامک/تماس تأیید داره (نه نصب واتساپ) — فرزانه یه گوشی قدیمی داره که
  این سیم توش جا می‌شه، پس این مانع نیست. معلوم نیست این شماره قبلاً
  روی واتساپ معمولی فعال بوده یا نه — باید موقع ثبت واقعی چک بشه.

**نقشه راه:**

| Stage | چیکار می‌کنیم | نیاز به چی |

**فایل‌های Stage 0:**
- `app/cleaner_roster.py` — روستر + مقادیر پیش‌فرض از `نظافتچی_ها-و-فرمول_های-مالی.md` (`data/cleaners.json`، gitignored، شماره‌های واتساپ هنوز خالی).

- `app/putzplan_writer.py` — تابع جدید `iter_open_rows()` (ردیف‌هایی که ستون A خالیه و کنسل نشدن).
- `app/tz.py` — رفکتور کوچیک: `BERLIN` timezone که قبلاً توی `checkin_reminder.py` بود، حالا مشترکه.

**تست‌شده (با دیتای شبیه‌سازی‌شده، نه فایل واقعی):**

- روی فایل واقعی (`python -m app.cleaner_coordination`، dry-run): ۳۴ ردیف باز پیدا شد، نزدیک‌ترین ۱۳ روز مونده (بیشتر از ۱۰) — درست هیچ اکشنی لاگ نشد، چون هنوز زوده.

**هنوز انجام نشده:** همه‌چیز بالای Stage 1 در جدول.

## ۱۱. بحث میزبانی عمومی (۲۰۲۶-۰۹-۲۴) — هنوز تصمیم نهایی نگرفته شده

فرزانه در این تاریخ خواست اول همین تصمیم رو باز کنیم. سه گزینه بررسی شد:

1. **کلاود همیشه‌روشن (VPS/Render/Fly.io/…)** — پایدارترین، ولی فایل‌های
   اکسل حساس (اسم مهمان، ایمیل، اسم نظافتچی، مبالغ مالی) باید یا رو خود
   سرور بیرونی نگه داشته بشن یا سینک بشن — یعنی داده از کامپیوتر شخصی
   خارج می‌شه. نگرانی امنیتی/حریم‌خصوصی.
2. **تونل موقت (Cloudflare Tunnel/ngrok) هر بار موقع اجرای لوکال** —
   ساده‌ترین برای شروع، فایل‌ها لوکال می‌مونن، ولی اگه کامپیوتر خاموش
   باشه یا اپ اجرا نشده باشه، جواب نظافتچی از دست می‌ره.
3. **رله از طریق وردپرس موجود (marktresidenz-eisenach.de)** — از
   `wordpress-plugin/marktresidenz-incoming-api.php` نیمه‌آماده استفاده
   می‌کنه؛ Twilio وب‌هوک رو به وردپرس می‌فرسته، وردپرس صف نگه می‌داره،
   اپ لوکال با polling می‌خونتش. مشکل «کامپیوتر خاموش» حل نمی‌شه (فقط
   دیرتر می‌شه) و پیام‌ها بی‌درنگ نیستن.

**گزینه‌ی چهارم که در همین بحث مطرح شد: سرور شخصی QNAP خانگی فرزانه** —
فرزانه یه QNAP NAS داره که تا حالا باهاش کار نکرده. اگه مدلش از
Container Station (Docker) پشتیبانی کنه، می‌شه کل اپ Flask رو مستقیم
روش اجرا کرد:
- NAS معمولاً ۲۴ساعته روشنه → هم مشکل «همیشه در دسترس بودن» حل می‌شه، هم
  فایل‌های حساس رو سخت‌افزار خودِ فرزانه می‌مونن (نه رو سرور شرکت دیگه،
  نه پخش بین دو سیستم مثل حالت وردپرس).
- نیاز به یه‌بار راه‌اندازی شبکه‌ای: باز کردن پورت رو روتر + DDNS
  (QNAP سرویس رایگان myQNAPcloud داره) + HTTPS (QNAP reverse proxy با
  Let's Encrypt داخلی داره).
- هنوز تست نشده که مدل NAS فرزانه از Container Station پشتیبانی می‌کنه
  یا نه.

**وضعیت:** فرزانه گفت می‌خواد بیشتر روی این تصمیم فکر کنه، تصمیم نهایی
گرفته نشده. توصیه‌ی این مکالمه: گزینه‌ی QNAP (چون هم «همیشه روشن» رو حل
می‌کنه هم داده حساس دست خودش می‌مونه)، ولی هنوز تأیید نشده. تا وقتی این
تصمیم گرفته بشه، فاز ۱ (Frontend) مستقل از این بحث و قابل شروع فوریه.

## ۱۲. میزبانی عمومی روی QNAP — انجام شد و تست شد (۲۰۲۶-۰۹-۲۵)

فرزانه تصمیم گرفت با QNAP بره جلو. کل مسیر راه‌اندازی همون روز انجام و
سر تا ته تست شد (از گوشی موبایل هم واقعاً باز شد). این بخش برای این
نوشته شده که یه مکالمه‌ی تازه بدون نیاز به مرور کل چت، دقیقاً بدونه
همه‌چیز کجاست.

### مشخصات NAS
- مدل: **QNAP TS-431P2** — ARM Cortex-A15 quad-core، ۸ گیگ رم، QTS 5.2.9.
- معماری: `armv7l` (این برای build کردن image پایتون مهمه، از base image
  چندمعماری مثل `python:3.11-slim` استفاده شده که خودش نسخه‌ی armv7 داره).
- IP محلی روی شبکه‌ی خونه: `192.168.178.21`، هاست‌نیم داخلی `Farzaneh-Steve`
  (این اسم عجیب از قبل روی NAS بوده، ربطی به این پروژه نداره).

### آدرس عمومی و شبکه
- **آدرس نهایی اپ از بیرون (گوشی/هرجا):**
  `https://farzaneh-nas.myqnapcloud.com:4844/`
- DDNS: myQNAPcloud، اسم دستگاه `farzaneh-nas`.
- گواهی SSL: رایگان (Let's Encrypt) از طریق myQNAPcloud، تمدید خودکار
  فعاله (معتبر تا ۲۰۲۶-۱۲-۲۳؛ اگه یه‌بار هم تمدید خودکار شکست بخوره،
  فقط هشدار «Not Secure» توی مرورگر میاد، چیزی از کار نمی‌افته — باید
  دستی از QNAP Overview → SSL Certificate چک/دوباره‌نصب بشه).
- Fritz!Box (روتر خونه، مدل 7490): چون ISP فقط بازه‌ی پورت بیرونی
  ۴۸۴۴-۴۸۶۳ رو می‌ده (نه هر پورتی، احتمالاً DS-Lite/IPv4 مشترک)، دو
  Portfreigabe روی دستگاه «Farzaneh-Steve» (`192.168.178.21`) تعریف شده:
  - بیرونی `4844` (TCP) → داخلی `8443` (نه ۴۴۳! پایین توضیح داده شده چرا)
  - بیرونی `4845` (TCP) → داخلی `80` (فعلاً بلااستفاده، برای آینده نگه
    داشته شده، می‌شه حذفش کرد اگه لازم نشد)
- **QNAP Reverse Proxy** (Control Panel → Netzwerkzugang → Reverse-Proxy):
  یه قانون به اسم `Ferienwohnung-App` که HTTPS روی پورت **۸۴۴۳** (نه ۴۴۳؛
  پورت ۴۴۳ رو خودِ پنل مدیریت QNAP قبلاً اشغال کرده بود، تداخل داشت) رو
  به `http://localhost:8000` (همون پورتی که container گوش می‌ده) forward
  می‌کنه.

### کد و container
- فایل‌های جدید اضافه شدن به ریپو: [`Dockerfile`](../Dockerfile)،
  [`docker-compose.yml`](../docker-compose.yml)، [`wsgi.py`](../wsgi.py)
  (نقطه‌ورود production، بدون `debug=True` — چون `run.py` با دیباگ روشن
  برای یه اپ عمومی خطرناکه)، [`.dockerignore`](../.dockerignore)، و
  `waitress` به [`requirements.txt`](../requirements.txt) اضافه شد
  (سرور WSGI ساده، بدون نیاز به کامپایل، مناسب ARM).
- اجرا با `waitress-serve` روی پورت داخلی ۸۰۰۰ داخل container.
- **کد روی NAS از طریق git نیومده** — چون NAS اصلاً `git` نصب نداره.
  به‌جاش یه tarball از پروژه (بدون `.git`, `backups/`, `data/`, `docs/`,
  `wordpress-plugin/`, فایل‌های حساس مثل `Pass.docx` و دو سند فارسی
  داخلی) ساخته و مستقیم با `scp` منتقل شد. مسیر روی NAS:
  `/share/CACHEDEV1_DATA/ferienwohnung-app`.
  **یعنی: هر تغییر کد بعدی، باید دوباره منتقل بشه (rsync/scp) و
  `docker compose up -d --build` دوباره اجرا بشه — به‌روزرسانی خودکار
  از گیت‌هاب هنوز طراحی نشده.**

### داده‌ها
- پوشه‌ی اشتراکی جدید روی NAS: **`Ferienwohnung-Data`**
  (`/share/CACHEDEV1_DATA/Ferienwohnung-Data`, symlink: `/share/Ferienwohnung-Data`).
  فقط اکانت `admin` بهش دسترسی Read/Write داره.
- داخلش: ۳ فایل اکسل (`GästeListe_2026K.xlsx`, `GästeListe_2026_Pf.xlsx`,
  `Putzplan2026.xlsx`) + پوشه‌ی `data/` (شامل `known_codes.json`,
  `quick_alerts.json`, `uploads/`, `import_staging/`) + پوشه‌ی `backups/`.
  همه‌شون از کامپیوتر فرزانه با توتال کامندر کپی شدن (نسخه‌ی محلی هنوز
  هم روی `E:\Gemeinsam\Ferienwohnung\Automat` باقی مونده، به‌عنوان نسخه‌ی
  احتیاطی، ولی دیگه اون نسخه توسط اپِ در حال اجرا خونده/نوشته نمی‌شه).
  یه پوشه‌ی `docs/` هم اونجا هست (کپی اسناد، اختیاری/بی‌ضرر).
- این پوشه با `volumes: /share/Ferienwohnung-Data:/data` توی
  `docker-compose.yml` مستقیم داخل container mount شده، و
  `DATA_DIR=/data` ست شده — یعنی container مستقیم روی همون فایل‌های
  واقعی می‌خونه/می‌نویسه، نه یه کپی جدا.
- `.env` واقعی (با `FLASK_SECRET_KEY`, `ADMIN_USERNAME`,
  `ADMIN_PASSWORD_HASH`, و بقیه) **فقط روی NAS** کنار `docker-compose.yml`
  نگه داشته می‌شه (`/share/CACHEDEV1_DATA/ferienwohnung-app/.env`)، هیچ‌وقت
  توی گیت نیست.
  **نکته‌ی فنی مهم که یه‌بار وقت گرفت:** مقدار `ADMIN_PASSWORD_HASH`
  (فرمت `pbkdf2:sha256:N$salt$hash`) شامل کاراکتر `$` هست. Docker Compose
  فایل `.env` رو برای جایگزینی متغیر توی `docker-compose.yml` هم می‌خونه،
  و `$` تک‌کاراکتری رو به‌اشتباه به‌عنوان شروع یه متغیر تفسیر می‌کنه (باعث
  warning و خالی‌شدن مقدار می‌شه). **راه‌حل: هر `$` توی مقادیر `.env` باید
  به‌صورت `$$` نوشته بشه** (فقط توی مقدار هش پسورد لازم بود، بقیه‌ی خطوط
  دست‌نخورده موندن).

### دسترسی SSH (برای خودکارسازی/دیباگ آینده)
- SSH روی NAS فعاله (پورت ۲۲، فقط داخل شبکه‌ی محلی، روی روتر باز نشده).
- یه کلید SSH اختصاصی (`ed25519`) ساخته و `authorized_keys`ش گذاشته شده
  توی **`/root/.ssh/authorized_keys`** (نه `homes/admin/.ssh` — اون یکی
  فقط پوشه‌ی شخصی فایل‌هاست، ربطی به لاگین SSH اکانت admin نداره؛ اکانت
  admin واقعاً به `/root` می‌ره).
- کلید خصوصی روی کامپیوتر فرزانه: `~/.ssh/id_ed25519_qnap`.
- **دستورات مهم روی NAS** (چون PATH پیش‌فرض SSH شامل مسیر Docker نیست
  و سوکت Docker مسیر غیراستاندارد داره):
  ```
  DOCKER=/share/CACHEDEV1_DATA/.qpkg/container-station/bin/docker
  export DOCKER_HOST=unix:///var/run/system-docker.sock
  cd /share/CACHEDEV1_DATA/ferienwohnung-app
  $DOCKER compose build      # بعد از تغییر کد
  $DOCKER compose up -d      # (--build هم اضافه کن اگه build جدید لازمه)
  $DOCKER logs ferienwohnung-automat     # دیدن لاگ‌ها
  ```

### تست نهایی
`curl https://farzaneh-nas.myqnapcloud.com:4844/` از بیرون (و از گوشی

## ۱۳. فاز ۲ (یادآوری چک‌این) — ساخته شد، هنوز به NAS منتقل نشده (۲۰۲۶-۰۹-۲۵)

**تصمیم نهایی طرح (تغییر کرد حین ساخت):** اول قرار بود یه چک روزانه
(کرون ۱۴:۰۰) باشه که «فردا مهمان میاد» رو چک کنه. فرزانه حین ساخت نظرش
عوض شد: **هیچ زمان‌بند روزانه‌ای نمی‌خوایم.** به‌جاش:
- همین که یه رزرو جدید از `/import` نوشته می‌شه، **فوراً** یه ایمیل
  یادآوری براش می‌ره (قلاب توی `xlsx_writer.process_batch`، بعد از
  ذخیره‌ی فایل‌ها).
- برای رزروهای آینده‌ای که از قبل توی فایل بودن (قبل از این فیچر)، یه
  دستور یک‌باره جداگانه هست: `python -m app.checkin_reminder` — همه‌ی
  رزروهای آینده رو چک می‌کنه و برای هرکدوم که قبلاً ایمیل نگرفته یادآوری
  می‌فرسته.
- خودِ **رویداد تقویم/آلارم توی ایمیل** (نه زمان ارسال ایمیل) رو فرزانه
  دقیق مشخص کرد: ساعت **۱۶:۰۰ به وقت برلین، یه روز قبل از Anreise**، با
  یه `VALARM` توی فایل `.ics` — باز کردن پیوست روی آیفون گزینه‌ی «افزودن
  به تقویم» رو می‌ده و بعدش خودِ iOS دقیقاً همون ساعت آلارم واقعی می‌ده
  (نه فقط نوتیفیکیشن ایمیل).

**فایل‌های جدید:**
- `app/checkin_reminder.py` — ساخت `.ics` + ارسال ایمیل (Gmail SMTP با
  App Password، نه پسورد اصلی جیمیل) + `maybe_send_reminder` (هیچ‌وقت
  استثنا پرت نمی‌کنه — اگه ایمیل fail بشه فقط لاگ warning می‌ده، ایمپورت
  اصلی نباید بشکنه) + `send_reminders_for_all_upcoming` (backfill).
- `app/notified_checkins.py` — همون الگوی `known_codes.py`، جلوگیری از
  ایمیل تکراری (`data/notified_checkins.json`، از قبل باید gitignore
  بشه مثل بقیه‌ی `data/`).

**تنظیمات لازم در `.env` (هنوز خالی، باید فرزانه پر کنه):**
```
GMAIL_USER=
GMAIL_APP_PASSWORD=
```
`NOTIFY_TO_EMAIL` اختیاریه، پیش‌فرض همون `GMAIL_USER` (یعنی به خودش
می‌فرسته). App Password باید از Google Account → Security → 2-Step
Verification → App Passwords ساخته بشه — پسورد اصلی جیمیل کار نمی‌کنه.

**نکته‌ی فنی:** `zoneinfo` (تبدیل ساعت برلین) روی پایتون محلی فرزانه
(۳.۸.۵) استاندارد نیست، فقط از ۳.۹ به بعد — `backports.zoneinfo` به
`requirements.txt` اضافه شد (import محافظت‌شده با try/except). روی NAS
(پایتون ۳.۱۱ توی Docker) مشکلی نیست ولی dependency هنوز لازمه چون
`tzdata` (خودِ دیتابیس IANA) توی image پایه نیست.

**تکمیل و رفع اشکال (۲۰۲۶-۰۹-۲۵، همون روز):**
1. `.env` لوکال پر شد (`GMAIL_USER`, `GMAIL_APP_PASSWORD`) و
   `python -m app.checkin_reminder` برای backfill همه‌ی ۴۸ رزرو آینده‌ی
   موجود (۱۶ کارل‌اشتراسه + ۳۲ آیزناخ) اجرا و موفق شد.
2. **باگ کشف‌شده و حل‌شده:** فرزانه گزارش داد پیوست `.ics` روی آیفونش
   دکمه‌ی «Add to Calendar» نشون نمی‌ده. علتش: **اپ Gmail روی iOS** با
   فایل‌های `.ics` که `METHOD:PUBLISH` دارن رفتار ویژه نداره (فقط
   پیش‌نمایش/دانلود)، برخلاف اپ Mail خودِ اپل که خودکار این دکمه رو نشون
   می‌ده. **راه‌حل نهایی (نه تغییر کد، تغییر گیرنده):** `NOTIFY_TO_EMAIL`
   روی `kontakt@marktresidenz-eisenach.de` ست شد — آدرسی که فرزانه با
   اپ Mail خودِ اپل (نه Gmail app) چکش می‌کنه. بعد از این تغییر، تست شد
   و آلارم درست به تقویم اضافه شد. `.env.example` و README این تصمیم رو
   مستند می‌کنن.
3. **فیچر جدید همون روز اضافه شد — ایمیل کنسلی:** فرزانه پرسید «اگه
   مهمون کنسل کنه چی، چطوری روزش رو از تقویم پاک کنم؟» — چون سیستم فقط
   یادآوری می‌فرسته، هیچ کنترلی روی تقویم واقعی آیفون نداره (رویداد یه‌بار
   با تاپ کردن خودِ فرزانه اضافه می‌شه، لینک زنده به سیستم نداره).
   راه‌حل: وقتی یه کدی که قبلاً براش یادآوری فرستاده شده کنسل بشه
   (`apply_cancellation` در `xlsx_writer.py`)، یه ایمیل دوم خودکار می‌ره
   («STORNIERT: ... — Kalendereintrag löschen») که دقیقاً می‌گه کدوم
   تاریخ/ساعت رو دستی از تقویم پاک کنه، به‌علاوه یه `.ics` با
   `METHOD:CANCEL` و همون UID به‌عنوان تلاش کمکی (ممکنه بعضی اپ‌های
   تقویم خودکار حذفش کنن، ولی تضمینی نیست — چون رویداد اصلی به‌صورت
   "invite زنده" اضافه نشده بود). اگه اصلاً یادآوری‌ای فرستاده نشده بود
   (مثلاً کنسلی خیلی زود اتفاق افتاد)، هیچ ایمیلی نمی‌ره — چیزی برای
   پاک کردن نیست.
   - `apply_cancellation` حالا به‌جای فقط تاریخ خروج، یه دیکشنری
     (`checkin`, `checkout`, `guest_name`, `confirmation_code`) برمی‌گردونه
     تا هم Putzplan (که فقط `checkout` می‌خواد) هم ایمیل کنسلی (که همه‌ی
     فیلدها رو می‌خواد) از یه فراخوانی جواب بگیرن.

**انتقال به NAS — انجام و تست شد (۲۰۲۶-۰۹-۲۵، همون روز):**
کد (تارباله با همون exclude-لیست `.dockerignore`) با `scp` منتقل شد،
`GMAIL_USER`/`GMAIL_APP_PASSWORD`/`NOTIFY_TO_EMAIL` به `.env` روی NAS
اضافه شد (بدون نیاز به `$$`-escaping، چون هیچ‌کدوم `$` نداره — برخلاف
`ADMIN_PASSWORD_HASH`)، `docker compose build && up -d` اجرا شد. تأیید
شد: کانتینر بدون خطا بالا اومد، `zoneinfo`/`tzdata` روی معماری ARM
(`armv7l`) مشکلی نداشت، آدرس عمومی (`https://farzaneh-nas.myqnapcloud.com:4844/`)
همچنان HTTP 200 می‌ده، و env varهای جدید داخل خودِ کانتینر درست خونده
می‌شن (چک‌شده با `docker exec`).

`data/notified_checkins.json` لوکال (۴۸ رکورد: ۱۶ کارل‌اشتراسه + ۳۲
آیزناخ) هم مستقیم به `/share/Ferienwohnung-Data/data/` روی NAS کپی شد
(`scp`) — تأیید شد از داخل container قابل‌دیدنه
(`/data/data/notified_checkins.json`, چون `DATA_DIR=/data`). یعنی اگه
از این به بعد رزروی روی NAS import بشه که یکی از این ۴۸ تا باشه (نباید
باشه، چون همون رزروهای موجودن)، دوباره ایمیل نمی‌ره.

**هنوز انجام نشده:**
1. تست واقعی end-to-end برای مسیر کنسلی (یه رزرو فیک بساز → یادآوری
   بگیر → کنسلش کن → ببین ایمیل استرو واقعاً می‌رسه و توضیح درست داره).
   تا الان فقط با دیتای فیک توی پایتون شبیه‌سازی شده (کار کرد)، نه از
   مسیر واقعی `/import`.

### ۱۷. Scheduler، کنسلی، یادآوری، مرخصی، داشبورد — ساخته شد، روی NAS در DRY-RUN (۲۰۲۶-۱۰-۰۱)

  ری‌استارت از state دوباره ساخته می‌شوند + یک چک بازیابی ۴۵ ثانیه بعد از
  شروع)، و دو کار روزانه: **۱۶:۰۰** (چک کامل — شروع ردیف‌هایی که به ۱۰/۳
  روز رسیده‌اند، یادآوری فردا، هشدار قرارداد) و **۱۹:۰۰** (کنسلی‌های
  بدون جایگزین + یادآوری‌های عقب‌افتاده). پیش‌فرض خاموش
  (`SCHEDULER_ENABLED`)، و dry-run (`SCHEDULER_DRY_RUN=1`).
- **کنسلی** (`app/day_before.py`): ردیف Putzplan «storniert» می‌شود، **حذف
  نمی‌شود**، ستون A (مسئول) می‌ماند → همان نفر شناخته می‌شود (حتی اگر
  دستی ثبت شده). پیام «entfällt» ساعت ۱۹:۰۰ شب قبل؛ اگر بعد از ۱۹:۰۰ شب
  قبل (یا همان روز) ثبت شود → **فوراً، حتی در ساعت آرامش** (تنها استثنا).
  اگر قبل از پیام کنسلی جایگزین بیاید → همان نفر می‌ماند؛ بعد از پیام →
  همان نفر اول با قالب `again` (Ja/Nein) پرسیده می‌شود (۱ ساعت صبر، حتی
  در پنجره‌ی broadcast)، بعد زنجیره از اول بدون او.
- رزرو جایگزین برای همان تاریخ، ردیف storniert Putzplan را **احیا** می‌کند
  (به‌جای ردیف دوم) — `append_putzplan_row`.
- **یادآوری ۱۶:۰۰** شب قبل به نفر ستون A (قالب `reminder_tomorrow`)،

- **مرخصی دو نوع** (state: `leave_weeks` سخت، `soft_weeks` نرم): سخت =
  هرگز پیام نمی‌گیرد؛ نرم = آخر زنجیره. جنیفر: سخت تا ۲۰۲۶-۱۰-۱۱.
- **داشبورد:** صفحه‌ی Putz-Alerts حالا «ثبت و شروع جستجوی نظافتچی» است و
  وضعیت هر ردیف را نشان می‌دهد، فرم «اعلام کنسلی» دارد؛ صفحه‌ی `/leave`
  برای مرخصی.

- **قبل از DRY_RUN=0:** نظافتچی‌های واقعی هنوز join Sandbox نکرده‌اند →
  اول شماره‌ی اختصاصی Twilio (سیم قدیمی) + approve قالب‌ها.
