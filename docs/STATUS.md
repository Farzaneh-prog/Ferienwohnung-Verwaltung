# وضعیت پروژه — سند انتقال (۲۰۲۶-۰۹-۱۶)

این فایل برای شروع یک مکالمه جدید نوشته شده — خلاصه‌ی دقیق «الان کجاییم»، بدون نیاز
به مرور تاریخچه طولانی مکالمه قبلی. اسناد اصلی (`سند-معماری-سیستم-مهمانخانه.md` و
`نظافتچی_ها-و-فرمول_های-مالی.md`) هنوز روی دیسک هستن و باید دوباره خونده بشن — این
فایل جایگزینشون نیست، فقط می‌گه واقعیت پیاده‌سازی‌شده کجاها با اون اسناد فرق کرده.

## ۳. مسیر داده — چطور یک رزرو وارد فایل می‌شود

۱. شما از Booking.com Extranet یا Airbnb Host، export رسمی می‌گیرید (نه Cowork، نه اسکرپینگ)
۲. `/import` → آپلود → `import_parser.py` تشخیص می‌ده فرمت کدومه و پارس می‌کنه
۳. اگه یه کد رزرو توی چند فایل باشه، `merge_reservation_entries` فیلد به فیلد **ترکیب** می‌کنه (نه فقط یکی رو انتخاب) — چون AA و AX به داده‌ی هم‌زمان از هر دو فایل بوکینگ نیاز دارن
۴. پیش‌نمایش (جدید/تکراری/کنسلی) → تأیید → `xlsx_writer.process_batch`
۵. `append_reservation`: ردیف جدید **فقط به یه ردیف خالی/انتهای شیت درست اضافه می‌شه**، هیچ‌وقت وسط شیت درج نمی‌شه (چون openpyxl هنگام درج/حذف ردیف، فرمول ردیف‌های دیگه رو خودکار اصلاح نمی‌کنه — بر خلاف خود اکسل)
۶. فرمول‌ها یا از یه ردیف مجاور «کپی» می‌شن (`clone_formulas`) یا برای ستون‌های حساس، **صریح نوشته می‌شن** (`EXPLICIT_FORMULAS`/`EXPLICIT_LITERALS`) — بخش ۵ رو ببینید
۷. کنسلی → هیچ‌وقت حذف نمی‌شه، فقط ستون `Storniert` (BB) = `ja` می‌شه (چون حذف فیزیکی هم همون مشکل فرمول رو داره)

## ۴. چیزی که هیچ export ای نمی‌ده — همیشه دستی

- **اسم مهمان و ایمیل**: هیچ‌کدوم از سه فرمت export (نه Booking ساده، نه مفصل، نه Airbnb) این رو نمی‌ده. همیشه placeholder (`Gast (Code XXXX)`) می‌مونه تا از `/complete` پر بشه
- **تعداد بزرگسال/کودک**: فقط توی Booking «مفصل» هست؛ Booking «ساده» و Airbnb ندارن
- **`/complete` فعلاً فقط ۴ فیلد داره**: اسم، ایمیل، بزرگسال، کودک — چیزهای دیگه‌ای که ممکنه لازم بشه (مثلاً اگه یه فیلد مالی از یه پلتفرم خاص نیومد) هنوز اضافه نشده؛ باید لیست دقیق «کدوم فیلد از کدوم پلتفرم میاد/نمیاد» کامل بشه و فرم بر همون اساس تکمیل بشه

## ۵. وضعیت دقیق هر ستون فرمولی (مهم‌ترین بخش برای بازبینی)

### ✅ صریحاً توسط شما تأیید و کد شده (`xlsx_writer.py`)
| ستون | فرمول/مقدار | منبع |
|---|---|---|
| I, J | `=F*G`, `=H*F` | ساختاری |
| M (Übernachtungssteuer) | `=G*F` | تأیید مستقیم |
| O (Gezahlt) | `=Preis+M` (Preis از export) | تأیید مستقیم |
| P (Putzarbeit) | Booking: نرخ ثابت ۵۰(Karlstraße)/۶۵(Eisenach) — Airbnb: `Reinigungsgebühr` واقعی | تأیید مستقیم |
| Z (Umsatzsteuersatz) | همیشه `0.19` | تأیید مستقیم |
| AA (Nettobetrag) | `Commission amount`(Booking) یا `Servicegebühr`(Airbnb) — هر دو پلتفرم؛ کامنت قدیمی کد که می‌گفت «فقط Booking» اشتباه بود، خودِ کد از اول برای هر دو کار می‌کرد، فقط کامنت ۲۰۲۶-۰۹-۱۶ اصلاح شد | تأیید مستقیم |
| AF (Endreinigung) | `=IF(R="ja",P,P/1.07)` — همه پلتفرم‌ها | تأیید مستقیم |
| AG (Stellplatz) | همیشه `0` | تأیید مستقیم |
| AK | `=IF(AQ="ja",AJ,AJ/1.07)` | تأیید مستقیم |
| AL | `=AK*1.07` | تأیید مستقیم |
| AM | `=AJ` | تأیید مستقیم |
| AV (متن پیام پرداخت) | فرمول کامل ۴حالته (Airbnb/booking/پرداخت‌شده/Vrbo) | تأیید مستقیم |
| AX (Payment Charge von Booking) | `Commission(ساده) − AA` — **فقط Booking** | تأیید مستقیم |
| BC (چک‌سام) | `=AF+AH+AN+AO+AP-AE+AG` | تأیید مستقیم |
| S | placeholder `0` | تأیید مستقیم (موقت، بعداً واقعی) |
| T | placeholder `3.5` | تأیید مستقیم (موقت) |
| U | `=T*12` | تأیید مستقیم |
| V | placeholder `"M-Ü"` | تأیید مستقیم (موقت) |
| AN (Zimmergesamt) | `=ROUND(AK*F,2)` | مستند در سند `نظافتچی_ها...` (۲۰۲۶-۰۹-۱۶ هاردکد شد) |
| AO (7% Steuer) | `=IF(AQ="ja","§13b UStG",ROUND((AN+AF)*0.07,2))` | مستند در سند (۲۰۲۶-۰۹-۱۶ هاردکد شد) |
| AP (19% Steuer) | `=IF(AQ="ja","§13b UStG",ROUND(AG*0.19,2))` | مستند در سند (۲۰۲۶-۰۹-۱۶ هاردکد شد) |
| AR (Netto) | `=AN+AF+AG+AH` | مستند در سند (۲۰۲۶-۰۹-۱۶ هاردکد شد) |
| AS (Zimmer) | `=ROUND(AK,2)` | مستند در سند (۲۰۲۶-۰۹-۱۶ هاردکد شد) |
| AT (متن Stellplatz) | Karlstraße: `IF(B="Airbnb",", exkl. Stellplatz.",IF(B="booking",", exkl. Stellplatz.","."))` / Eisenach: همون با «inkl.» (بر اساس property نه sheet؛ ۲۰۲۶-۰۹-۱۶ فرمول nested-IF دقیق جایگزین نسخه‌ی OR() شد که رفتارش یکی بود ولی متنش فرق داشت) | مستند در سند + تأیید مستقیم |
| AU (Komm-label) | `=IF(B="Airbnb","Airbnb Bestätigungscode: ",IF(B="booking","Booking number: "," "))` | مستند در سند (۲۰۲۶-۰۹-۱۶ هاردکد شد) |
| BE (Verdient pro nacht) | `=Q/F` | مستند در سند (۲۰۲۶-۰۹-۱۶ هاردکد شد) |
| Q (Verdient) | `=IF(B="booking",O-U-M-AA-AX-AO,O-U-M-AA-AX-AO-AP)` | تأیید مستقیم ۲۰۲۶-۰۹-۱۶ |
| AB | `=AA*0.19` | تأیید مستقیم ۲۰۲۶-۰۹-۱۶ |
| AC | `=AA+AB` | تأیید مستقیم ۲۰۲۶-۰۹-۱۶ |
| AE | `=O` | تأیید مستقیم ۲۰۲۶-۰۹-۱۶ |
| AH | `=M` | تأیید مستقیم ۲۰۲۶-۰۹-۱۶ |
| AI | `=IF(AQ="ja",AE-AF-AG-AH,AE-AF*1.07-AG*1.19-AH)` | تأیید مستقیم ۲۰۲۶-۰۹-۱۶ |
| AJ | `=AI/F` | تأیید مستقیم ۲۰۲۶-۰۹-۱۶ |

**نتیجه:** بخش «⚠️ کپی از ردیف مجاور، تأییدنشده» قبلی (Q، AB، AC، AE، AH، AI، AJ
+ AN، AO، AP، AR، AS، AT، AU، BE) کاملاً بسته شد — همه‌ی این ۱۵ ستون الان یا از
سند طراحی یا مستقیم توسط فرزانه (۲۰۲۶-۰۹-۱۶) تأیید و هاردکد شدن.

### ❌ همیشه خالی می‌مونه — تصمیم دستی/کسب‌وکاریه
`K (Private Zweck)، R (Ausländische Firma)، W (Fahrtkosten)، AD (Adresse)،
AQ (Ausländische Firma - همون هدر تکراری)، AW (bereits überwiesen)،
AY (Paypal)، AZ (رزرو برای فلگ مالیات، فاز بعد)`

**L (Arbeitszweck) — تصمیم نهایی ۲۰۲۶-۰۹-۱۶: دستی می‌مونه.** سن کودک واقعاً
توی export «مفصل» Booking هست (`Children's age(s)`)، ولی فرزانه ترجیح داد
خودش دستی وارد کنه؛ گفت اگه اصلاً واردش نکنه هم مهم نیست. پس نه پارسر تغییر
کرد، نه فرمی برای K/L ساخته شد — عمداً.

**X (Rechnungsnummer) — تصمیم نهایی ۲۰۲۶-۰۹-۱۶: دستی می‌مونه.** برای همه‌ی
رزروها لازمه، ولی باید دقیقاً به ترتیب تاریخ ورود شماره‌گذاری بشه — و چون
ردیف‌های جدید ممکنه توی شکاف وسط شیت درج بشن نه لزوماً انتهای فیزیکی
(بخش ۶.۴ بالا)، یه شمارنده‌ی خودکار ساده («آخرین X زوج + ۲») نمی‌تونه تضمین
کنه ترتیب تاریخی درست بمونه وقتی یه رزرو با تاریخ قدیمی‌تر بعداً اضافه بشه.
فرزانه تشخیص داد خودش دستی انجام بده راحت‌تره.

## ۶. کشف‌های فنی مهم (برای جلوگیری از تکرار اشتباه)

1. **`ws.cell(row, col, value=None)` در openpyxl هیچ کاری نمی‌کنه** (چون `None`
   سنتینل «مقداری داده نشده»ست) — همیشه `cell.value = None` مستقیم.
2. ستون‌های `R` و `AQ` **دقیقاً همون متن هدر** رو دارن (`Ausländische Firma mit
   steuer in Heimat`) — نگاشت بر اساس اسم هدر نمی‌تونه بینشون فرق بذاره؛ برای همین
   فرمول‌های `EXPLICIT_FORMULAS` مستقیم با حرف ستون (نه اسم فیلد) آدرس‌دهی می‌شن.
3. برخی ردیف‌های قدیمی، فرمول رو به‌صورت **متن/عدد چسبونده‌شده** دارن نه فرمول زنده
   (مثلاً `AV` گاهی متن ثابت بود، `BC` نسخه‌ی قدیمی/ناقص فرمول رو داشت) — یعنی
   «کپی از ردیف مجاور» به‌تنهایی قابل‌اعتماد نیست.
4. ردیف‌های خالی وسط شیت (از پاک‌کردن دستی قبلی با Delete، نه حذف کامل ردیف) به‌عنوان
   «جای خالی قابل‌استفاده» در نظر گرفته می‌شن — ردیف جدید می‌تونه توی یه شکاف وسط
   شیت بیفته، نه لزوماً انتهای فیزیکی؛ این عمدیه (امن‌تر از همیشه انتهای شیت).

## ۷الف. کنسلی‌ها + پاک‌کردن دستی — `known_codes.json` (۲۰۲۶-۰۹-۲۳)

فرزانه ردیف‌های کنسل‌شده رو کامل از GästeListe پاک می‌کنه (نه فقط
Storniert=ja)، چون جمع‌کل‌های سالانه (Übersicht/ÜbersichtSteuer) فرمول
`SUM()` ساده‌ن — حدود ۲۷۱ فرمول توی هر دو فایل، هیچ‌کدوم Storniert رو
حساب نمی‌کنن — و پاک‌کردن تنها راهی بود که جمع‌ها درست بمونن. مشکلش این
بود که پاک‌کردن یعنی هیچ ردی از کد رزرو نمی‌مونه، پس یه export قدیمی‌تر که
دوباره آپلود بشه، اون رزرو رو «جدید» می‌بینه و دوباره اضافه می‌کنه (این
دقیقاً همون چیزی بود که با `HMEX45DNAJ` دیدیم).

**راه‌حل انتخاب‌شده (نه SUMIFS):** `app/known_codes.py` — یه فایل JSON
جدا (`data/known_codes.json`، از قبل gitignore شده) که هر کدی که این اپ
تا حالا اضافه یا کنسل کرده رو برای همیشه نگه می‌داره، مستقل از خودِ
GästeListe. `get_existing_confirmation_codes` (چک تکراری‌بودن ایمپورت)
الان این لیست رو هم چک می‌کنه. تست شد: اضافه → دستی پاک از اکسل → دوباره
آپلود همون کد → درست به‌عنوان تکراری رد شد.

**چرا نه SUMIFS:** تبدیل ۲۷۱ فرمول به `SUMIFS(..., BB:BB, "<>ja")` هم
جواب می‌داد، ولی روی ارقام مالیاتی اثر می‌ذاره و نیاز به بازکردن فایل
واقعی توی اکسل برای تأیید اعداد داشت — فرزانه این راه سبک‌تر و بدون‌ریسک
رو ترجیح داد.

**یافته‌ی جانبی که هنوز حل نشده:** شیت `Muster` اصلاً ستون `Storniert`
رو توی هدرش نداره (برخلاف شیت‌های فصلی که BB='Storniert' دارن) — یعنی
اگه یه رزروِ پارک‌شده توی Muster (سال بعد) کنسل بشه، `apply_cancellation`
نمی‌تونه پرچمش کنه (بی‌صدا رد می‌شه). با راه‌حل `known_codes.json` این
دیگه مشکل دِدوپ ایجاد نمی‌کنه، ولی خودِ ستون Storniert توی Muster هنوز
خالیه — اگه لازم شد جدا درستش کنیم.

## ۷. Putzplan (برنامه نظافتچی) — خودکارسازی جدید (۲۰۲۶-۰۹-۲۲)

`Putzplan2026.xlsx` — یه فایل کاملاً جدا از GästeListe، یه شیت تخت
(`Tabelle1`) بدون هیچ فرمولی، ۱۰ ستون (A تا J؛ جزئیات کامل هر ستون توی
`app/putzplan_writer.py`). از این به بعد، هر رزرو جدیدی که از `/import`
تأیید بشه یه ردیف خودکار اینجا هم می‌گیره — `app/putzplan_writer.py`،
وصل‌شده به `xlsx_writer.process_batch`.

**نکته‌ی مهم — ستون C اول اشتباه فهمیده شده بود:** اولین نسخه‌ی این ماژول
فرض کرد ستون C (Datum) تاریخ *ورود* مهمانه (بر اساس تطبیق آماری با
GästeListe که گمراه‌کننده بود، چون فایل به‌مرور دستی دریفت کرده). فرزانه
همون روز تصحیح کرد: **ستون C تاریخ *خروج* مهمانه** (Abreise) — چون نظافت
معمولاً به محض خروج مهمان انجام می‌شه. قبل از اینکه نسخه‌ی اشتباه به داده‌ی
واقعی برسه اصلاح شد.

**نگاشت نهایی:**
- **C (Datum)** = Abreise Datum (خروج) رزرو
- **D (Tag)** = روز هفته‌ی همون تاریخ خروج
- **F (Buchung für gleichen Tag)** = «Ja» اگه رزرو *بعدی* (نزدیک‌ترین
  Anreise غیرکنسلی بعد از این خروج، توی همون ملک) دقیقاً همون روز باشه
- **G, H (Erwachsene, Kinder unter 18)** — **تصحیح ۲۰۲۶-۰۹-۲۴:** تعداد
  بزرگسال/کودک **رزرو بعدی** (کسی که داره میاد)، نه رزروی که داره خارج
  می‌شه — چون نظافتچی باید بدونه برای چند نفر باید خونه رو آماده کنه، نه

  تعداد مهمان رزروِ خارج‌شونده رو می‌نوشت؛ ۵ ردیف واقعی که با منطق قدیمی
  ساخته شده بودن دستی اصلاح شدن.
  - چون «رزرو بعدی» همیشه موقع ساخت ردیف معلوم نیست (هنوز بوک نشده، یا

  دلیلی برای چندواحدی بودن — گزارش شد؛ فرزانه خودش همون روز (۲۰۲۶-۰۹-۲۴)
  دستی این ۳ ردیف رو اصلاح کرد).

  ستون J می‌نویسه `storniert` — دقیقاً همون قراردادی که خود فایل قبلاً

هیچ تلاشی برای اصلاح یا بازسازی گذشته نشده و نمی‌شه.

**هنوز ساخته نشده — نیاز به منبع داده‌ی جدید داره:** فرزانه یه قانون

## ۸. زیرساخت Cowork/WordPress — بلااستفاده فعلاً

`wordpress-plugin/marktresidenz-incoming-api.php` (نصب‌شده روی
marktresidenz-eisenach.de) و `tools/apply_incoming.py` برای مسیر «Cowork مستقیم
Airbnb/Booking رو می‌خونه» ساخته شده بودن. چون اون مسیر به‌خاطر ToS متوقف شد،
این زیرساخت الان **بلااستفاده‌ست** ولی حذف نشده — می‌تونه برای چیز دیگه‌ای
(مثلاً دریافت هشدار نظافتچی از راه دور) دوباره استفاده بشه، یا اگه تصمیم گرفتید
کلاً لازم نیست، می‌شه پاکش کرد.

## ۹. سؤالات باز که باید در بازبینی جواب داده بشن

1. **رزروهای کنسل‌شده‌ی قدیمی** که از قبل توی فایل هستن (نه از export جدید) —
   چطور شناسایی/پرچم بشن؟ راه خودکار نداریم.
2. **کنسلی Airbnb** — export ایربنب اصلاً ستون وضعیت نداره؛ راه‌حل جایگزین لازمه.
3. **`/complete` باید چه فیلدهایی داشته باشه** — لیست دقیق «چی از کجا میاد/نمیاد».
   ~~فعلاً همون ۴ فیلد فعلی (اسم، ایمیل، بزرگسال، کودک) کافیه — تا وقتی کمبود
   واقعی توی استفاده دیده نشه چیزی اضافه نمی‌شه.~~
4. ~~**ستون‌های فقط-کپی‌شده (بخش ۵)**~~ — **حل شد ۲۰۲۶-۰۹-۱۶.** همه‌ی ۱۵ ستون
   (AN/AO/AP/AR/AS/AT/AU/BE از سند + Q/AB/AC/AE/AH/AI/AJ تأیید مستقیم) هاردکد
   شدن. L و X هم تصمیم نهایی گرفتن: هر دو دستی می‌مونن (بخش ۵ رو ببین).
5. **مرتب‌سازی فیزیکی ردیف‌ها** — عمداً انجام نمی‌شه (ریسک فرمول)؛ اگه واقعاً لازمه،
   باید یه ابزار جدا و محتاط برای بازسازی دوره‌ای کل شیت طراحی بشه.
6. **آینده‌ی Cowork/WordPress** — تصمیم به تعویق افتاد تا فاز ۵ (واتساپ نظافتچی)؛
   ممکنه به‌عنوان رله‌ی وب‌هوک ورودی Twilio دوباره استفاده بشه (به میزبانی عمومی
   Flask بستگی داره — هنوز تصمیم نگرفته شده).
7. **فازهای بعدی طبق سند اصلی** (ایمیل خودکار مهمان، واتساپ نظافتچی، انتشار
   گیت‌هاب نهایی) — اولویت‌بندی مجدد لازمه با توجه به تغییر مسیر فاز ۲.
8. **اسکیلیشن Putzplan** (بخش ۷) — بستن مهمانخانه یه شب و سپردن به رامش وقتی
   نه ترنداور فشرده هست نه نظافتچی در دسترس — منتظر ساخته‌شدن روستر
   در‌دسترس‌بودن نظافتچی‌ها.
